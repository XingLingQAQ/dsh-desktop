# 桌面悬浮宠物 — 设计

状态：**提案，未写代码**。下面是功能、交互、以及会碰到的硬约束。

> **开工前已实测过的一件事（重要）**：我原本以为这台机器透明合成不可靠，会逼出一个"挂件面板"方案。**实测结果是透明可用**，所以宠物可以真的"漂浮"在桌面上，不需要画一个方块面板。
> 测法：起了一个 `transparent(true)` 的置顶无边框窗口，左半边画不透明红块、右半边留空，然后抓屏像素。红块右侧的像素**不是**统一填充色，而是混入了无关的桌面内容（`(68,120,210)`、`(12,12,12)`）——说明留空处确实透出了底下的东西。
> 之前"透明不可靠"的印象来自**更新弹窗**：那个窗口用圆角区域裁剪（`SetWindowRgn`）而不是透明，且**桌面壳页面本身不透明**（`background: var(--ds-bg-1)`），两件事被记串了。

---

## 1. 一句话

主窗口关掉之后，桌面上留一只常驻的宠物。它能被摸、被喂，能**替你收发对话**（有新消息会说、能直接回一句），也能**接住你拖过来的文件**并把它喂给当前会话。

---

## 2. 技术形态：透明置顶异形窗口

实测确认可行，所以壳就是**最直接的那种**：

```
不透明无所谓 → 透明窗口 + 无边框 + 置顶 + 跳过任务栏
形状         → 由 CSS 决定（图片 + 透明背景），不需要 SetWindowRgn
点击         → 宠物以外的透明区域要么穿透、要么由我们自己做命中测试（见 §3.3）
```

**但有一个平台差异必须处理**：Windows 上 `transparent(true)` 的 Tauri 窗口，透明区域**默认仍然吃掉鼠标事件**（窗口是矩形，透明不等于穿透）。
- 想要"点宠物才有反应，点宠物旁边的空气 = 点桌面"，需要在透明像素上做**点击穿透**（`WS_EX_TRANSPARENT` + 动态开关，或按 alpha 动态切换）
- 我倾向 **不做点击穿透**：宠物窗口做小（贴着宠物轮廓），用户不会觉得旁边那块"空气"碍事；做了穿透反而引入"有时点得到有时点不到"的不稳定感
- 这条**建议你确认**（见 §8 决策 A）

## 3. 为什么不能直接抄 whale-girl

`whale-girl` 有一个桌面伴侣（`plugins/whale-girl/desktop/`，独立 Tauri 壳 + Node 引擎）。**它是最好的参考，但不能当基础**：

| 原因 | 说明 |
|---|---|
| **它是别人的插件** | 我们不 fork。宠物**外观**可以借用任何素材，但**壳**必须是我们自己的 |
| **它是"连上去"的架构** | 它连 DSH 的 HTTP 端点（`/state`、`/events`、`/presence`、`/interact`），需要那个插件在跑。我们要的是**壳自带**的能力，不依赖某个第三方插件装了没 |
| **它已经很重** | 那套资历/等级/称号系统加上去，就变成了重复建设 |

**所以：外观可以借鉴，机制必须自己写。**

### 3.1 RDP 约束（这条真的会咬人）
这是 RDP 会话，之前做更新弹窗时踩过：**拿不到真实前台窗口、轮询焦点无效**。当时最后的解法是用 **Raw Input（`RIDEV_INPUTSINK`）** 接"用户点了窗外"。

对宠物的影响：
- ❌ 不能靠"窗口失焦"判断该不该收气泡 → 要用点击位置判断
- ❌ 不能靠前台窗口判断"用户在用别的 app，别打扰" → 要么不做这类礼貌逻辑，要么用别的手段（比如空闲时间用 `GetLastInputInfo`）
- ✅ 抓屏在 RDP 下**可用**（上面实测就是这么做的），但**窗口不在前台时 `PrintWindow` 才可靠**，`CopyFromScreen` 会抓到别的东西——自动化测试要注意

### 3.2 三种形态

**形态 1：常驻宠物（主体）**
- 约 `160×180`，透明，置顶，跳过任务栏
- 可拖到任意位置，位置记忆（多显示器要存显示器标识）
- 平时只有宠物本体，鼠标移上去才浮出小操作提示

**形态 2：气泡（交互时出现）**
- 约 `300×380`，独立的置顶窗口，点击宠物弹出
- 内容：消息列表 / 快速回复框 / 文件队列
- 点外部或 Esc 关闭——**关闭判定走 Raw Input**（见 3.1）

**形态 3：落点（拖拽接收）**
- 把文件拖到宠物身上 → 宠物"接住"，进队列
- 透明区域的命中由我们自己算：读光标坐标 + 和宠物轮廓比对（宠物是固定图，轮廓可以预先存成一张掩码）

## 4. 功能清单

### 4.1 陪伴（基础层）
| 功能 | 说明 |
|---|---|
| 待机动画 | 眨眼、呼吸、偶尔走动/打盹 |
| 位置记忆 | 拖到哪，下次还在哪；多显示器要存显示器 id |
| 开机自启 | 可选，跟主窗口一起起来 |
| 摸头/投喂 | 点击有小反馈（不做成 whale-girl 那套等级系统，太重） |

### 4.2 对话（核心价值）
| 功能 | 说明 | 数据从哪来 |
|---|---|---|
| **新消息提醒** | 会话有新回合结束时，宠物做提示动作 + 出气泡 | 主窗口已经有的 `session-observer` 插件在报当前会话；回合结束事件需要新增 |
| **快速回复** | 气泡里一个输入框，直接往当前会话发一条 | 需要宿主的 session 服务（见 §5） |
| **状态反映** | 思考中/等批准/出错 → 对应动作 | 同上 |
| **会话切换** | 气泡里列出最近会话，点一下切主窗口过去 | 需要 session 列表 |

### 4.3 文件（差异化）
| 功能 | 说明 |
|---|---|
| **接住文件** | 拖文件到宠物 → 进队列 |
| **喂给会话** | 队列里点"发送" → 文件进当前会话（作为附件或路径引用） |
| **暂存区** | 队列可留到下次；可看到缩略图/文件名/大小 |
| **拖出来** | 从气泡把文件拖到别处（同 §3 形态 3 的难点） |

### 4.4 快捷操作
- 右键宠物 → 小菜单：打开主窗口 / 新会话 / 切换会话 / 设置 / 退出
- 和现有托盘菜单**共用一套菜单定义**，不重复实现

## 5. 对话能力怎么接 —— **已实测通过**

这一节原来列了三条待验项。现在三条**全部在运行中的宿主里实测过**了，不是在源码里读出来的。

做法：临时加了一个宿主半插件 `plugins/dsh-desktop-probe`（只读探测 + 一个可控的发送路由），
让它在真实的 DSH 宿主里回答。**这个插件已删除**，结论留在下面。

### 5.1 列出会话 —— 可以

| 来源 | 调用 | 实测结果 |
|---|---|---|
| **活着的**（本进程内） | `ctx.get('agents').list()` / `.get(id)` / `.roots()` | 存在，方法齐全 |
| **活着的** | `ctx.get('sessions').list()` / `.get(id)` | 存在 |
| **落盘的**（含冷会话） | `ctx.get('sessionQuery').listSessions()` | **返回 23 条**历史会话，形状 `{ header, live, persisted }` |

**一个坑**：`sessionQuery` 的搜索是**被配置关掉的**——实测报
`session search is disabled: this deployment configures the session-query index with openAt "never"`。
所以「列出会话」能用，「搜索会话」不能用。

### 5.2 往已有会话发消息 —— 可以

**用 `sessionController`，不要用 `agents.followup`。** 这是这次最重要的一个结论：

```js
const sc = ctx.get('sessionController')

// 建会话（本身也是幂等的 create-or-adopt）
const { sessionId } = await sc.create({ cwd?, sessionId?, agentPreset? })
// → { sessionId: "session-<uuid>", agentPreset: "standard" }

// 发消息 —— 宠物要的就是这一句
await sc.prompt({
  requestId: <客户端生成的唯一 id>,
  sessionId,
  mode: 'queue' | 'steer',
  content: [{ type: 'text', text: '...' }],
}, signal)
// → { accepted: true }
```

**为什么不用底层的 `agents.get(id).followup(...)`**：`sessionController.create` 本身是
**create-or-adopt**（活着就直接返回那个 agent、落盘的走 `resume`、都没有才新建），
而且它带一道**子 agent 归属围栏**，`AgentRegistry` 自己没有。走控制器既少写代码，又是
Web UI 已经在走的那条路。

**实测**：`create` 返回 `session-c1b73094-…` + `agentPreset: "standard"`，
`prompt` 返回 `{ accepted: true }`；随后 `liveSessions` / `liveAgents` 都变成 1，
`agents.get(sessionId)` 拿到真实的 Agent 对象。

**`requestId` 是必需的**：它是「持久化在那条被接受的消息上的客户端 id」，inbox 拿 `id`
做唯一性键，重复会抛。文档示例里漏了它。要自己造就用 `crypto.randomUUID()`；更稳的是用
平台自己的 `createUserMessage` —— 实测**可以**从插件里够到（`file:///` 路径下裸
`@deepseek-ai/*` import 解析不了，要走 `createRequire` + 路径列表，`dsh-desktop-mcp`
里已有这个写法），它自己会生成 `id`。

### 5.3 观察回合结束 —— 可以，但 `turn/end` **不等于**「成功」

```js
ctx.on('session/event', (session, event) => { ... })
```

实测一次真实回合收到的（共 33 条 `session/event`）：

```
turn/start(seq 4) → step/start → system/message → user/message → request/header
→ session/title(13) → assistant/attempt → step/end(31) → turn/end(32)
```

事件名是 `event.type`，**不是** `event.kind`（whale-girl 的注释里记着这个坑：
历史上把 kind 当 type 用，导致 turn 边沿永不匹配）。信封是 `{ type, seq, time, data }`。

**关键**：这次 `turn/end` 的 `reason.kind` 是 **`error`**，`reason.error.code` 是 **`SERVER`**
（这台环境连不上模型，重试 7 次后失败）。

所以 `turn/end` **只说明回合结束了，不说明它成功了**。whale-girl 把「非 blocked 的
`turn/end`」一律当成 `done`——照抄的话，**失败的回合会让宠物庆祝**。第 2 期必须按
`reason.kind` 分支：

| `reason.kind` | 宠物该有的反应 |
|---|---|
| `completed` | 完成（庆祝） |
| `error` | 出错（`reason.error.code` 给错误码） |
| `blocked` | 等待批准（waiting） |
| `aborted` / `interrupted` | 被打断 |
| `max-tokens` | 被截断 |

**另外三个可用信号**（都实测到了）：

| 事件 | 载荷 | 用途 |
|---|---|---|
| `agent/status` | `{ agent, status: 'idle' \| 'running' }` | 不用轮询的「忙/闲」 |
| `agent/assistant-stream` | `{ agent, frame }`，`frame.type` 是 `start`/`chunk`/`end` | **逐字流式**，气泡里能边想边显示 |
| `agent/turn-stopping` | `{ agent, turn, signal }`（serial，回合边界提交前 await） | 想在收尾时插一句 |

从普通插件上下文注册的监听是**未打标签**的，会收到**所有**会话的事件，不用挨个订阅。

**没验的**：这台环境连不上模型，所以只观察到 `error` 结尾的回合，**没观察到一次
`completed` 的回合**。上表里除 `error` 外的分支是按 `TurnEndReason` 类型写的，不是实测的。

## 6. 架构

```
主窗口（关掉时隐藏，不退出）
  ├── content webview（DSH 页面）—— 关掉后不工作，所以宠物不依赖它
  └── pet 窗口（常驻，可关）
        ├── 渲染：React + 帧动画（CDN 无依赖，和 tray-menu 同构）
        ├── 壳能力：Tauri IPC（拖拽位置、显隐、开机自启）
        └── 数据：新增一个宿主半插件 plugins/dsh-desktop-pet/
              ├── ctx.webServer 挂同源路由（读会话/发消息/文件队列）
              └── 落盘：<dshHome>/pet/（位置、队列、设置）
```

**关键决定：宠物不依赖主窗口的 webview。** 主窗口关闭时 `content` 可能被销毁，所以宠物要活，它需要的能力必须来自**宿主半插件**（那条路在宿主进程里，和窗口无关）。

## 11. 第 1 期：实际做了什么，以及踩到的两个真 bug

**实现**：`src-tauri/src/pet.rs`（窗口、位置、落盘）、`src/pet.tsx`（宠物本体与交互）、
`src/styles.css` 的 `.pet-*` 段、托盘菜单加一项开关。

**两个在真机上才暴露、光看代码看不出来的问题**：

1. **宠物窗口没有 capability，拖拽和主题监听全被拒绝。**
   `capabilities/default.json` 的 `windows` 列表里没有 `pet`。Tauri v2 的权限是**按窗口**发的，所以
   `startDragging()`（第 1 期的核心交互）和 `listen('theme-changed')` 都会抛权限错误。
   窗口能显示、能摆位置，唯独拖不动——很容易被当成"拖拽实现写错了"。

2. **托盘菜单会把整个应用锁死。**
   `show_tray_menu` 原来在**没有菜单窗口时就地 `build()`**。建 webview 会派发到主线程并等待，
   而它的两个调用方（托盘图标事件、宠物右键命令）本来就跑在主线程上——于是主线程等自己，
   所有 IPC 挂起。这不是宠物引入的：**右键托盘图标本来就会锁死**。
   修法是把菜单窗口在启动时预建好（和更新弹窗、宠物一样），`show_tray_menu` 只负责摆位置和显示。

**顺带修掉的三处坐标问题**：

- 宠物位置改用 `PhysicalPosition` + `SystemParametersInfo(SPI_GETWORKAREA)`。原来混用逻辑像素，
  在缩放环境下会差一个系数。
- 菜单按"可见卡片"而不是"窗口矩形"做边界收拢——窗口带一圈看不见的调整边框（这里左右各 8px、
  上方 1px），按窗口矩形收拢会让卡片正好压出屏幕边缘。
- 托盘图标传来的坐标物理/逻辑混用，缩放下会摆错位置。

**实测过的**（都在运行中的应用里量过，不是看代码推的）：

| 项 | 结果 |
|---|---|
| 默认位置 | `2184,840` = 工作区右下角内缩 24px，精确吻合 |
| 位置记忆 | 拖动后落盘 `x/y/monitor`，重启回到原位 |
| 透明 | 截屏见壁纸透出；页面自身 `html/body/root` 背景均为 `rgba(0,0,0,0)` |
| 待机动画 | `pet-breathe` / `pet-blink` / 耳朵抖动三条都在跑 |
| 被摸反应 | `data-mood` 切到 `happy`，弹跳 + 腮红 + 星星 + 影子收缩，1.1s 后回待机 |
| 减弱动效 | 循环动画停、**点击反应保留**（这是刻意的取舍） |
| 拖动 | `startDragging()` 返回成功 |
| 关主窗口 | 主窗口隐藏、**应用与宠物都还在** |
| 托盘开关 | 显示/隐藏宠物都生效，状态落盘 |
| 右键菜单 | 宠物贴底时**向上展开**，可见卡片完全落在工作区内 |

**没验的**：多显示器、非 100% 缩放、以及"在宠物外面点一下菜单会不会自己收起来"
（这台机器的会话没有交互桌面，合成点击送不到窗口）。

## 12. 第 2 期：状态反映 + 气泡

**实现**：

| 文件 | 干什么 |
|---|---|
| `plugins/dsh-desktop-pet/index.js` | 宿主半：订阅 `session/event`，推出 `GET /dsh-desktop-pet/state` |
| `src-tauri/src/host.rs` | `http_get_body()`：给宿主路由用的最小 HTTP GET |
| `src-tauri/src/lib.rs` | `start_pet_state_watch()`：每 600ms 拉一次，变了就 `emit("pet-state")` |
| `src/pet.tsx` + `src/styles.css` | 六种表情：思考 / 执行工具 / 等待批准 / 完成 / 出错（+ 被摸） |
| `src/pet-bubble.tsx` + `pet-bubble.html` | 气泡窗口：会话标题 + 当前状态 + 最近回合结果 |

**为什么状态走宿主半**：宠物住在桌面上，主窗口关掉时 DSH 页面就没了——而那正是宠物
唯一存在的时刻。所以状态必须在**宿主进程**里推导，那是会话真正所在的地方。

**为什么宠物自己去不了那个路由**：宠物是壳窗口，宿主是另一个源。壳本来就知道宿主在哪，
所以由壳去取、再用 Tauri 自己的事件通道转给宠物。

**表情设计的一条原则**：只用已经存在的零件（眼睛、耳朵、嘴、腮红），不新增图形——
每个表情都是同一只宠物在变，而不是换了一张脸。只有"出错"动颜色（去饱和 + 变暗），
其余全靠姿态：宠物在屏幕角落，余光扫过去时姿态比颜色好读。

### 12.1 一个会毁掉整个应用的真 bug：登录 cookie 无限堆积

**症状**：DSH 页面打不开，显示 `HTTP ERROR 431`。

**根因**：宿主每次启动都会给 Web UI 发一个以 token 命名的登录 cookie
（`dsh-auth-<token>`，30 天有效期），**没有任何东西清理它们**。每次启动多加约 173 字节，
而 Chromium 拒绝发送请求头超过约 2KB 的请求，它自己的基础头部就占掉大半。
实测这台机器上积了 **69 个 cookie、约 15.6KB**，于是应用自己的页面在跑任何一行代码之前
就被 431 拒了。

**这不是宠物引入的**，是启动次数攒出来的——任何人都迟早会撞上。

**修法**：挂载 DSH 之前先清掉上次留下的 cookie，只留本次的。实测这个 webview 里的
cookie **69 个全是登录 cookie**，没有别的东西要保。清理必须**同步做完**再挂载，
因为会撞 431 的正是子 webview 的第一个请求；而且必须**在独立线程上**做——Tauri 明确
记录了这些 cookie 调用在同步命令/事件处理里会死锁。

### 12.2 又一个按窗口发权限的坑：气泡窗口

`pet-bubble` 不在 `capabilities/default.json` 的窗口列表里。后果和宠物当初一样隐蔽：
**窗口能显示、能渲染、样式全对，但收不到 `pet-state` 事件**（所以卡片永远是空的），
Escape 的 `hide()` 也会被拒。症状看起来像"气泡没接上数据"，实际是权限。

> 这已经是同一类问题第二次咬人了（第 1 期是宠物拖不动）。**新增任何窗口，先看
> `capabilities/default.json` 的 `windows` 列表里有没有它。**

### 12.3 实测过的

一次真实回合的完整链路（宿主发布 → 壳轮询 → Tauri 事件 → 宠物换脸）：

```
20:09:23  host=idle     | pet mood=idle
20:09:23  host=thinking | pet mood=thinking   ← turn/start
20:09:38  host=error    | pet mood=thinking
20:09:39  host=error    | pet mood=error      ← 约一拍（600ms）后跟上
20:09:53  host=idle     | pet mood=error
20:09:54  host=idle     | pet mood=idle       ← 15s 错误停留期结束
```

**关键**：它显示的是 `error` 而**不是** `done`。whale-girl 把"非 blocked 的 `turn/end`"
一律当完成——照抄的话**失败的回合会让宠物庆祝**。这条差异是实测出来的，不是推的。

气泡在回合中打开的内容（与宿主一致）：

```json
{ "tone": "busy", "state": "正在思考…", "session": "probe12 ok", "foot": "第 1 回合 · 点宠物关闭" }
```

六种表情逐项量过计算样式，每个都确实不同（耳朵角度、眼睛缩放、嘴形、忙碌点）。

### 12.4 第三个问题：孤儿宿主（**已修，见 §13.1**）

调试时 UI 发消息一直被服务端拒绝：

```
SessionAlreadyOwnedError: session "..." is already owned by an active write handle
```

根因不在产品逻辑，在**强杀**：我反复用 `Stop-Process -Force` 杀壳进程，那样**不会走
`RunEvent::Exit`**，于是它 spawn 的 DSH 宿主被留成孤儿。实测积了 **12 个孤儿宿主**
（最早一个是 9/21 的），每个都占着会话的写租约。

**这对用户也是真的**：应用崩溃、或者从任务管理器结束进程，都会留下孤儿宿主，
而症状是"发消息没反应"——非常难查。修法见 §13.1。

## 13. 第 3 期：发消息 + 会话切换（含 §12.4 的修复）

### 13.1 先修孤儿宿主：让内核负责，而不是让清理代码负责

上一节说"修法是启动时清理父进程已死的宿主"。**那个思路是错的**——它要靠一段清理代码
去跑，而问题恰恰是"清理代码没机会跑"。

正确的做法是 **job object**：宿主 spawn 出来后立刻放进一个带
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 job。这个 flag 的语义是"最后一个 job 句柄关闭时，
杀掉 job 里的所有进程"，而**进程死亡时操作系统会关闭它的句柄**——不管它是正常退出、
崩溃，还是被任务管理器强杀。于是"宿主跟着壳一起死"变成了内核的职责，不需要任何一行
我们的代码被执行。

句柄故意**不关闭**（存成 `isize` 泄漏掉）：关闭它就是触发点，让它随进程消亡而由系统回收
才是我们要的语义。

**实测**（`scripts/host-orphan-test.ps1`）：按父进程找到宿主 → `Stop-Process -Force` 强杀壳
→ 5 秒后宿主**已消失**，壳下剩余子进程 **0**。修复前同样的操作会留下孤儿。

> 顺带一提，这也是为什么"启动时杀所有 DSH 宿主"是错的：这台机器上同时跑着**别的** DSH
> 宿主（比如正在执行这段对话的那个），按名字杀会把它一起干掉。job object 天然只影响
> 我们自己 spawn 的那一个。

### 13.2 新增的路由与命令

| 层 | 东西 | 作用 |
|---|---|---|
| 宿主 | `GET /dsh-desktop-pet/sessions` | 活会话 ∪ 落盘会话，30 条上限，带 `live` 标记 |
| 宿主 | `POST /dsh-desktop-pet/prompt` | `{sessionId, text}` → `{ok}` 或 `{ok:false, error:{code,message}}` |
| 宿主 | `POST /dsh-desktop-pet/select` | 把宠物**钉**到某个会话上 |
| 壳 | `pet_sessions` / `pet_send_prompt` / `pet_select_session` | 转成 Tauri 命令给气泡用 |
| 气泡 | 会话选择器 + 输入框 + 发送按钮 | — |

**「钉住」的语义**：默认跟随"最近有动静的会话"，这在默认情况下对、在用户**明确指定**一个
之后就不对了。所以显式选择优先。但当**另一个**会话开始新回合时，钉子会被摘掉——用户
明显已经去别处干活了，宠物还赖在旧选择上就是错的。

**失败信息必须原样透传**。宿主拒绝时的 `error.message` 里带着原因（实测：
`SessionAlreadyOwnedError: … already owned by an active write handle`），气泡直接显示它。
把它换成"发送失败"会让这类问题彻底无法排查——上面那个孤儿宿主 bug 就是这么找出来的。

### 13.3 实测过的

| 命令 | 结果 |
|---|---|
| `pet_sessions` | 26 个会话，字段 `[id, title, activity, live, updatedAt]` |
| `pet_select_session` | 切换成功，返回新 current |
| `pet_send_prompt` | `{"ok":true}`，宿主随即 `activity=thinking, turn=1` |
| 空文本 | `{"ok":false,"error":{"code":"invalid-request","message":"text is required"}}` |
| 空 sessionId | `{"ok":false,"error":{"code":"invalid-request","message":"sessionId is required"}}` |

**完整闭环**：在气泡里选中一个会话 → 从宠物发一句话 → 回合跑起来 → 学到标题
（`title: "probe-ui: 只回复 ok"`）→ 状态与表情跟上（`lastEnd: {kind:"error", code:"SERVER"}`）。

## 14. 第 4 期：文件接住 + 队列 + 喂给会话

### 14.1 一个必须先查清的问题：prompt 到底怎么带文件

**答案和直觉相反：契约里根本没有"本地路径"这种东西。**

`PromptContentPart` 只有三个变体（`dsh-api-session-controller/lib/types/types.d.ts`）：

```ts
| { type: 'text';  text: string }
| { type: 'image'; mediaType: ImageMediaType; data: string; name?: string }
| { type: 'file';  receiptId: Branded<'file-upload-receipt-id'> }
```

`file` 那个变体带的是一张**不透明收据**（"Host-minted authority for one staged file
upload in one Agent scope"），不是路径。所以真实流程是**先上传、再引用收据**：

```js
const handle = await ctx.get('fileUploads').uploadStream({ sessionId, data, name })
// → 收据
content.push({ type: 'file', receiptId: handle.receiptId })
```

收据是**按会话**授权的（`stagedFiles = new WeakMap()`，键是 `agent.session`），
拿别人的收据会 `FILE_NOT_STAGED`。

**顺带排除一个诱人的错误答案**：`dsh-file-reference` 从名字看很像，但它只是 `@` 提及的
自动补全（返回 `{path, kind}`），注入的是**文本**——正是"仅仅提一句"那种我们不要的效果。

### 14.2 实现

| 层 | 东西 |
|---|---|
| `src-tauri/src/pet_files.rs` | 队列本体：去重、校验、落盘、启动时丢弃已被移动/删除的条目 |
| `src-tauri/src/lib.rs` | 宠物窗口的 `DragDrop` 事件 → 入队 → 广播 `pet-queue`；四个命令 |
| 宿主 | `POST /prompt` 增加 `files: string[]`：逐个 `stat` → `createReadStream` → `uploadStream` → 组块 |
| `src/pet.tsx` | 投放提示圈 + 待发送角标；并 `preventDefault` 掉浏览器的默认行为 |
| `src/pet-bubble.tsx` | 文件列表（中间截断、保留扩展名）+ 逐个删除 + 清空 + 带文件发送 |

**几个刻意的选择**：

- **校验全部前置**。只有"被投递的 prompt"才会让收据失效，所以一批文件传到一半失败会
  留下孤儿收据。因此所有路径在**写第一个字节之前**全部检查完（绝对路径、存在、是普通文件）。
  相对路径**拒绝而不是解析**——宿主的 cwd 是 harness 的，解析会静默换成另一个文件。
- **图片按普通文件走，不用 `image` 变体**。`image` 要求 base64 进请求体（毁掉流式，
  也和 64KiB 体积上限冲突），而且宿主会按模型模态拦截，不支持就直接拒掉整个 prompt。
  代价要说清楚：**通过 `files` 附上的 `a.png` 会变成一条句柄，模型用文件工具去读，
  不是内联视觉。**
- **队列只在宿主接受后才清空**。拒绝通常是有原因、可修的（比如会话被占用），
  先清空等于拿用户的文件换一条错误信息。
- **气泡窗口高度 172 → 235**。卡片是**底部对齐、向上生长**的：空的时候和以前逐像素相同，
  有文件时向上长、远离宠物。235 是"三行文件 + 两行失败信息"不裁切所需的值；停在 172 会把
  顶部 63px 裁掉。

### 14.3 实测过的

| 项 | 结果 |
|---|---|
| 真实文件上传 | **`{"ok":true}`** —— 证明 `fileUploads` 服务在这个发行版里确实挂载了 |
| 路径不存在 | `invalid-request`，消息里点名是哪个路径 |
| 相对路径 | `invalid-request`：`file path must be absolute: relative.txt` |
| 目录 | `invalid-request`：`not a file: …` |
| 不带 files（旧路径） | `{"ok":true}`，行为不变 |
| 气泡渲染队列 | 文件名、大小、`2 个文件 · 906 B`、清空按钮都在 |
| 带文件发送 | `{"ok":true}` → 队列**自动清空** → 宿主 `activity=thinking, turn=2` |

### 14.4 没验的
- **OS 级拖放本身**。CDP 的合成拖拽（`Input.dispatchDragEvent`）到不了 Tauri 的
  `DragDrop` 事件——实测拖完队列仍是 0。这台机器的会话没有交互桌面，也没法从资源管理器
  真拖一个文件。所以**处理函数背后的命令验过了，OS 把事件送到处理函数这一步没有**。
  作为补偿，宠物页面把 `dragover`/`drop` 的默认行为 `preventDefault` 掉了：万一 Tauri
  那一层没拦住，浏览器的默认行为是**导航到被拖入的文件**，宠物窗口会变成一个文本文件，
  而且没有退路。这一层防的不是"功能不工作"，是"功能不工作时很难看"。
- **模型侧最终看到的那行句柄文本**。宿主接受了、回合跑起来了，但 `fileHandleText` 生成的
  实际文本没有观察到（会话日志是 zstd 压缩的，这台机器上没有可用的解压模块）。

## 15. 新消息提醒 + 一处有理由的偏差

### 15.1 新消息提醒（§4.2 里唯一没做的一条）

**为什么这条最重要**：宠物存在的理由就是"主窗口关着的时候"。而在这之前，回合结束只是
**悄悄换一张脸**——屏幕角落里 132px 的一张变了的脸，很容易整个错过。

**规则**：回合结束时，如果**主窗口可见**就不提醒（记录就在眼前，变脸够了）；
**主窗口不可见**才提醒。提醒**不自己消失**——会自己淡掉的东西，恰恰是走开一会儿的人
回来时看不到的那种。只有打开气泡才清掉，那正是它在要的动作。

**实现**：壳的轮询里记住上次看到的 `lastEnd.at`，变了就判断主窗口是否可见。第一次
观察到**不提醒**——否则刚启动时会拿上一轮遗留的 `lastEnd` 报一次早就结束的回合。

> 一个具体的坑：判断主窗口可见性必须用 `get_window("main")` 而不是
> `get_webview_window("main")`。后者在 DSH 内容作为子 webview 挂上之后会返回 `None`
> （窗口明明还在），于是**每一次回合结束都会被当成"用户没在看"**。

**实测**（`scripts/pet-notify-test.py`，三个方向都测了）：

| 场景 | 结果 |
|---|---|
| 主窗口**可见**时回合结束 | `missed: no` —— 不打扰 |
| 主窗口**隐藏**时回合结束 | `missed: error`，角标 `!`，带会话标题 |
| 打开气泡（走宠物自己的处理函数） | `missed: no` —— 清掉 |

### 15.2 偏差：「会话切换」做成了钉住宠物，而不是切主窗口

§4.2 的原话是「气泡里列出最近会话，点一下**切主窗口过去**」。**我没有那样做**，改成
「把宠物钉到那个会话上」。理由：

1. **主窗口关着的时候没法"切过去"**——而那正是宠物唯一存在的场景。钉住则在关着的时候
   照样有用：宠物开始汇报那个会话，你也可以直接对它说话。
2. 实测主窗口的 URL 里**没有会话 id**（`location.href` 就是 `http://127.0.0.1:<port>/`），
   所以"切过去"只能去点 DSH 自己的侧边栏 DOM——依赖别人的 DOM 结构，很脆。

所以这是一个**有理由的偏差**，不是漏做。如果确实想要"切主窗口"，那是另一件事，
需要驱动 DSH 界面。

### 15.3 顺带发现：子 agent 会话会出现在选择器里
实测报错：

```
session "73671091-…" is owned by subagent routing
```

子 agent 的会话和普通会话存在同一个语料里，而且最新的时候排在最前面。宿主**正确拒绝**
了对它发 prompt（错误信息也很清楚），但选择器里它和普通会话长得一样、可以点。
目前不改：那条错误信息本身足够可读，而且用户可能确实想**看**一个子 agent 会话，
只是不能对它说话。

## 16. 一次对抗式审查，以及它抓到的洞

四期做完之后，我让一个子 agent 做了一次**对抗式审查**（只读、专门找缺陷）。它抓到了
几个我自己没看见的问题，其中一个是**功能级的**。值得记下来，因为它们都属于"测试方法
本身有盲区"这一类。

### 16.1 最严重的一个：点击宠物**打不开气泡**

**症状**：点宠物没有任何反应。没有选择器、没有输入框、没有文件队列，而且新加的新消息
角标**永远清不掉**（清它的唯一入口就是打开气泡）。气泡自己的脚注还写着「点宠物关闭」
——那个动作同样是坏的。

**根因**：`startDragging()` 进入的是**窗口管理器的模态拖拽循环**，它把鼠标捕获到顶层
窗口直到按键抬起；而那一次抬起**结束循环、并且不会被送到 WebView2 子窗口**。所以页面
永远收不到 `mouseup`——而 `bubble()` 恰恰只挂在那个 `mouseup` 上。

**为什么我完全没发现**：**我所有测试都是直接 `invoke` 命令打开气泡的**，一次都没点过。
`pet-motion.py` 的注释里甚至写着"用键盘事件而不是点击，因为 mouse-down 会交给窗口管理器"
——那句话说的就是这个机制，我读过它，却没有把它和"点击打不开气泡"联系起来。

**修法**：**不在 mouse-down 时开始拖拽**。改成监听 `pointermove`，只有移动超过 4px 才把
拖拽交给 OS。这样纯点击根本不进入那个循环，它的 `mouseup` 正常送达。

**验证到哪一步**：合成 `mousedown` + `pointerup`（无移动）→ 宠物被摸（`happy`）+ 气泡
打开（`visible: true`）。**但这证明的是处理链完整，不是修复本身**——合成的抬起事件无论
如何都会被渲染器送达。修复的正确性在于「mouse-down 时不再调用 `startDragging()`」，
这一条是**代码层面**成立的（`onMove` 是唯一调用点，且未达阈值直接返回）。真正验证需要
一台有交互桌面的机器上用真鼠标点一下。

### 16.2 其余已修的

| 问题 | 后果 | 修法 |
|---|---|---|
| 三个宠物命令是**同步**的，会在 UI 线程上做阻塞 socket I/O | 宿主一慢，整个壳（主窗口重绘、托盘菜单、宠物拖动）冻结数秒 | 改成 `async` |
| 所有宿主调用共用 1.5 秒超时 | 发消息要上传文件，超过 1.5 秒会把**已经送达**的 prompt 报成失败，用户会再发一次 | 轮询用 1.5s，用户等待的用 30s |
| `prune_stale_auth_cookies` 想保留的 cookie 名**不可能存在** | 实际在删全部 `dsh-auth-*`（今天只被调用顺序掩盖）；重试启动会删掉正在用的那个，页面所有 `/api` 变 401 | 删掉那个错的参数；用 `CONTENT_ATTACHED` 显式保证「只在页面认证之前清理」 |
| 队列上限 20，宿主上限 10 | 攒到 11 个就**永远发不出去**，只能一个个删，且没人告诉你 | 两边对齐到 10 |
| 发送成功清空**整个**队列 | 发送期间拖进来的文件被无声丢掉，用户以为已经附上了 | 只移除**实际发出去的那些** |
| 提醒只比较 `lastEnd.at` | **切换会话**时会为二十分钟前结束的回合弹角标 | 按 `(会话, 时间)` 判定 |
| 状态文件原地写 | 中断（这个项目天天被强杀）留下截断文件 → 位置**和 `enabled`** 一起重置，于是关主窗口会直接退出应用 | 临时文件 + 改名 |

### 16.3 审查里"确认没问题"的部分（同样有价值）

它逐项核过并明确说没问题的：**每个窗口都在 `capabilities` 里**、cookie 调用不在会死锁的
线程上、状态轮询只启动一次且隐藏时不做 I/O、位置防抖每个手势只起一个 worker、
宠物窗口事件处理里没有自锁、气泡 268×235 的尺寸预算**刚好**放得下最坏情况、
所有 `useEffect` 都有清理（除了上面那个 `onUp`）、`PET_VISIBLE` 和文件里的 `enabled`
没有"两个写者"问题。

> 它明确列"检查过且没问题"的清单，这一点很有用——否则沉默会被误当成"没看过"。

### 16.4 没修的（记在这里，不假装不存在）

- **多显示器**：气泡和菜单按**主显示器**的工作区收拢，宠物拖到副屏后气泡会被拉回主屏。
  宠物自己的定位是跨显示器的，所以这是代码层面的不一致。修它需要 `monitor_from_point`，
  而验证需要第二块屏。
- **上传中途失败会留下已暂存的收据**（宿主没有公开的"取消暂存"接口）。
- **宿主返回非 2xx 时，它自己的 JSON 错误被丢掉**，只剩一句通用的"取不出去"。
- **`/sessions` 的单飞没有超时**：`listSessions()` 若不返回，选择器会一直空着直到插件重载。
- **插件里的 `sessions` Map 只增不减**；**忙状态不衰减**（只老化 done/error）。

> §16.4 的**多显示器**一条已在下面 §17 修掉（`window_work_area`）。

## 17. 第二次对抗式审查：15 条，全部核过并修了

切了 agent（handover）之后又做了一次对抗式审查，这次 15 条。主题和上次一样——**"测试
方法本身有盲区"**：绝大多数都是"直接 invoke 命令验，从没走真实路径"漏掉的。每一条的
DSH 事件/接口契约都**先对着本机在跑的宿主源码核过**（`%APPDATA%\DeepSeek Harness\
runtime\dsh\node_modules\@deepseek-ai`），不是照记忆猜。修复按**文件切给三个子 agent 并行**
（读源码是只读、驱动应用要独占，而三个文件集互不相交，所以并行零冲突）：插件半
`index.js` 一个、Rust 壳 `lib.rs/pet.rs/host.rs` 一个、气泡 UI 两个 tsx 一个。

**整体验证**：`tsc` 干净、`cargo check` 干净（4 条既有 warning，均不在改动处）、Vite 生产
构建干净。其中**唯一会静默打断壳↔宿主通道的风险**——给所有路由加 `sameOrigin` 会不会
把壳自己的轮询也挡掉——**静态证伪了**：壳的 `http_request` 只发 `Host`/`Connection`/
`Content-Type`，**不带 `Origin`**，所以 `sameOrigin` 对壳一律放行，只挡外站页面。

### 17.1 三个功能级的（最要紧）

- **`blocked` 被当成"等待你批准"，而真正的批准根本没接**。DSH 里 `blocked` 是 preStep
  钩子**否决了这一步、回合已经结束**（`turn/end` 的一种 `reason.kind`），不是在等人。真正
  的批准是回合**进行中**由 `dsh-user-approval` 追加的 `approval/asked`（带 `toolName`）→
  `approval/decided`。原来把 `blocked` 映射成 `waiting`，而 `waiting` 又是唯一**永不过期**
  的表情——于是钩子一否决，宠物就永远卡在"等待批准"；反过来真需要批准时又只显示"正在
  执行工具"。**修法**：`blocked` 归入 done（回合结束、无模型错误）；新接 `approval/asked→
  waiting`、`approval/decided→thinking`。顺带 `tool/result` 也接上（原来只接 `tool/call`，
  工具跑完后的一整段回答里宠物一直写着"正在执行 bash"）。
- **新消息提醒漏掉每个会话的第一次回合结束**。原逻辑要求 `!first && same_session` 才提醒，
  但一个会话第一次结束前没有基线，`same_session` 恒为假，于是第一次结束被吞掉；上次"实测
  三方向通过"是因为测试脚本先在同一会话里跑了一轮、恰好造出了基线。**修法**：改成
  `seen_session`+`baseline_end` 的按会话基线——新成为当前的会话**静默**采基线（它此刻的结束
  是旧闻），只有**同一会话把基线往前推**才提醒。这样既压住"宠物出现前就结束的回合"和
  "切进来的旧会话"，又能抓住**开始盯之后的第一次结束**。
- **气泡的会话选择器加载不出来**。气泡窗口在启动时就建好，那时宿主还没起，挂载时的拉取
  静默失败；而 `/state` 在有会话产生事件前一直报 `sessionId: null`，所以按 `sessionId` 变化
  重试的那条路永远不触发。结果：开着宠物、不碰任何会话就关主窗口、点宠物 → 没有选择器、
  输入框禁用（"没有可以发送的会话"），哪怕盘上有几十个会话。**修法**：气泡窗口每次**变可见**
  时重拉（`visibilitychange`），且**第一次 `pet-state` 到达且列表仍空**时也补拉；单个会话也
  可选（`>= 1`）。

### 17.2 两个"修复自身可能引入的倒退"

- **附着到已运行宿主时，别清 cookie**。清理只在**我们自己冷启动**时对：旧 cookie 都是旧端口
  的、新页面靠 `?token=` 自己铸新的。但**附着路径**（DSH 已在 17890/3080 上跑）没有新 token，
  页面靠的就是那个已运行宿主的 30 天 cookie——清掉它，`/` 和每个 `/api` 全 401。**修法**：
  `finish_launch` 里读 `state.attached`，附着就跳过清理。
- **防孤儿的 job 会连带杀掉 DSH 故意分离启动的程序**。Node 的 `detached: true` 从不传
  `CREATE_BREAKAWAY_FROM_JOB`，所以宿主的全部后代都被 `KILL_ON_JOB_CLOSE` 的 job 圈住、随壳
  一起死——包括 DSH 打算比自己活得久的程序（从会话里打开的编辑器等），**每次正常退出都杀**。
  上一期"job 只覆盖我们 spawn 的那一个"这个说法不成立。**修法**：加
  `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`——分离的后代能脱离 job，宿主自身因为不传 breakaway
  仍随壳而死。

### 17.4 没验的 / 仍是 follow-up（如实说）

- **交互桌面才能验的三条**：Alt+F4 隐藏（合成关闭事件必达，证明不了"真按一下"）、双击去抖
  （同理）、以及 §16.1 的点击打开——都在**代码层面**成立，真机需要一台有交互桌面的机器用
  真鼠标。
- **`visibilitychange` 在 Tauri 隐藏/显示窗口时是否真触发**：WebView2 对 `ShowWindow` 一般会
  发，但这台机器没交互桌面没实按；`pet-state` 首达补拉是它的兜底，两者一起覆盖了报告里的
  复现，但这条值得在真机上盯一眼。
- **`approval/asked` 那张脸没有真实触发验证**：需要一个真会触发工具批准的回合，这次没造。
  事件名和 payload 都对着源码核过了。
- **`turn/end` 后 `waiting` 表情期间会显示上一个工具名**（`asked` 时设、下一个 `tool/result`/

- **#10 的 requestId 幂等**：只做了壳侧加长超时，真正的"重试不重复"要插件铸一次性 id、UI
  透传，跨三层，留作 follow-up。
