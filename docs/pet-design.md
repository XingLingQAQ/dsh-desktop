# 桌面悬浮宠物 — 设计

状态：**提案，未写代码**。下面是功能、交互、以及会碰到的硬约束。

> **开工前已实测过的一件事（重要）**：我原本以为这台机器透明合成不可靠，会逼出一个"挂件面板"方案。**实测结果是透明可用**，所以宠物可以真的"漂浮"在桌面上，不需要画一个方块面板。
> 测法：起了一个 `transparent(true)` 的置顶无边框窗口，左半边画不透明红块、右半边留空，然后抓屏像素。红块右侧的像素**不是**统一填充色，而是混入了无关的桌面内容（`(68,120,210)`、`(12,12,12)`）——说明留空处确实透出了底下的东西。
> 之前"透明不可靠"的印象来自**更新弹窗**：那个窗口用圆角区域裁剪（`SetWindowRgn`）而不是透明，且**桌面壳页面本身不透明**（`background: var(--ds-bg-1)`），两件事被记串了。

---

## 1. 一句话

主窗口关掉之后，桌面上留一只常驻的宠物。它能被摸、被喂，能**替你收发对话**（有新消息会说、能直接回一句），也能**接住你拖过来的文件**并把它喂给当前会话。

---

## 2. 技术形态：透明置顶异形窗口

实测确认可行，所以壳就是**最直接的那种**：

```
不透明无所谓 → 透明窗口 + 无边框 + 置顶 + 跳过任务栏
形状         → 由 CSS 决定（图片 + 透明背景），不需要 SetWindowRgn
点击         → 宠物以外的透明区域要么穿透、要么由我们自己做命中测试（见 §3.3）
```

**但有一个平台差异必须处理**：Windows 上 `transparent(true)` 的 Tauri 窗口，透明区域**默认仍然吃掉鼠标事件**（窗口是矩形，透明不等于穿透）。
- 想要"点宠物才有反应，点宠物旁边的空气 = 点桌面"，需要在透明像素上做**点击穿透**（`WS_EX_TRANSPARENT` + 动态开关，或按 alpha 动态切换）
- 我倾向 **不做点击穿透**：宠物窗口做小（贴着宠物轮廓），用户不会觉得旁边那块"空气"碍事；做了穿透反而引入"有时点得到有时点不到"的不稳定感
- 这条**建议你确认**（见 §8 决策 A）

## 3. 为什么不能直接抄 whale-girl

`whale-girl` 有一个桌面伴侣（`plugins/whale-girl/desktop/`，独立 Tauri 壳 + Node 引擎）。**它是最好的参考，但不能当基础**：

| 原因 | 说明 |
|---|---|
| **它是别人的插件** | 我们不 fork。宠物**外观**可以借用任何素材，但**壳**必须是我们自己的 |
| **它是"连上去"的架构** | 它连 DSH 的 HTTP 端点（`/state`、`/events`、`/presence`、`/interact`），需要那个插件在跑。我们要的是**壳自带**的能力，不依赖某个第三方插件装了没 |
| **它已经很重** | 那套资历/等级/称号系统加上去，就变成了重复建设 |

**所以：外观可以借鉴，机制必须自己写。**

### 3.1 RDP 约束（这条真的会咬人）
这是 RDP 会话，之前做更新弹窗时踩过：**拿不到真实前台窗口、轮询焦点无效**。当时最后的解法是用 **Raw Input（`RIDEV_INPUTSINK`）** 接"用户点了窗外"。

对宠物的影响：
- ❌ 不能靠"窗口失焦"判断该不该收气泡 → 要用点击位置判断
- ❌ 不能靠前台窗口判断"用户在用别的 app，别打扰" → 要么不做这类礼貌逻辑，要么用别的手段（比如空闲时间用 `GetLastInputInfo`）
- ✅ 抓屏在 RDP 下**可用**（上面实测就是这么做的），但**窗口不在前台时 `PrintWindow` 才可靠**，`CopyFromScreen` 会抓到别的东西——自动化测试要注意

### 3.2 三种形态

**形态 1：常驻宠物（主体）**
- 约 `160×180`，透明，置顶，跳过任务栏
- 可拖到任意位置，位置记忆（多显示器要存显示器标识）
- 平时只有宠物本体，鼠标移上去才浮出小操作提示

**形态 2：气泡（交互时出现）**
- 约 `300×380`，独立的置顶窗口，点击宠物弹出
- 内容：消息列表 / 快速回复框 / 文件队列
- 点外部或 Esc 关闭——**关闭判定走 Raw Input**（见 3.1）

**形态 3：落点（拖拽接收）**
- 把文件拖到宠物身上 → 宠物"接住"，进队列
- 透明区域的命中由我们自己算：读光标坐标 + 和宠物轮廓比对（宠物是固定图，轮廓可以预先存成一张掩码）

## 4. 功能清单

### 4.1 陪伴（基础层）
| 功能 | 说明 |
|---|---|
| 待机动画 | 眨眼、呼吸、偶尔走动/打盹 |
| 位置记忆 | 拖到哪，下次还在哪；多显示器要存显示器 id |
| 开机自启 | 可选，跟主窗口一起起来 |
| 摸头/投喂 | 点击有小反馈（不做成 whale-girl 那套等级系统，太重） |

### 4.2 对话（核心价值）
| 功能 | 说明 | 数据从哪来 |
|---|---|---|
| **新消息提醒** | 会话有新回合结束时，宠物做提示动作 + 出气泡 | 主窗口已经有的 `session-observer` 插件在报当前会话；回合结束事件需要新增 |
| **快速回复** | 气泡里一个输入框，直接往当前会话发一条 | 需要宿主的 session 服务（见 §5） |
| **状态反映** | 思考中/等批准/出错 → 对应动作 | 同上 |
| **会话切换** | 气泡里列出最近会话，点一下切主窗口过去 | 需要 session 列表 |

### 4.3 文件（差异化）
| 功能 | 说明 |
|---|---|
| **接住文件** | 拖文件到宠物 → 进队列 |
| **喂给会话** | 队列里点"发送" → 文件进当前会话（作为附件或路径引用） |
| **暂存区** | 队列可留到下次；可看到缩略图/文件名/大小 |
| **拖出来** | 从气泡把文件拖到别处（同 §3 形态 3 的难点） |

### 4.4 快捷操作
- 右键宠物 → 小菜单：打开主窗口 / 新会话 / 切换会话 / 设置 / 退出
- 和现有托盘菜单**共用一套菜单定义**，不重复实现

## 5. 对话能力怎么接 —— **已实测通过**

这一节原来列了三条待验项。现在三条**全部在运行中的宿主里实测过**了，不是在源码里读出来的。

做法：临时加了一个宿主半插件 `plugins/dsh-desktop-probe`（只读探测 + 一个可控的发送路由），
让它在真实的 DSH 宿主里回答。**这个插件已删除**，结论留在下面。

### 5.1 列出会话 —— 可以

| 来源 | 调用 | 实测结果 |
|---|---|---|
| **活着的**（本进程内） | `ctx.get('agents').list()` / `.get(id)` / `.roots()` | 存在，方法齐全 |
| **活着的** | `ctx.get('sessions').list()` / `.get(id)` | 存在 |
| **落盘的**（含冷会话） | `ctx.get('sessionQuery').listSessions()` | **返回 23 条**历史会话，形状 `{ header, live, persisted }` |

**一个坑**：`sessionQuery` 的搜索是**被配置关掉的**——实测报
`session search is disabled: this deployment configures the session-query index with openAt "never"`。
所以「列出会话」能用，「搜索会话」不能用。

### 5.2 往已有会话发消息 —— 可以

**用 `sessionController`，不要用 `agents.followup`。** 这是这次最重要的一个结论：

```js
const sc = ctx.get('sessionController')

// 建会话（本身也是幂等的 create-or-adopt）
const { sessionId } = await sc.create({ cwd?, sessionId?, agentPreset? })
// → { sessionId: "session-<uuid>", agentPreset: "standard" }

// 发消息 —— 宠物要的就是这一句
await sc.prompt({
  requestId: <客户端生成的唯一 id>,
  sessionId,
  mode: 'queue' | 'steer',
  content: [{ type: 'text', text: '...' }],
}, signal)
// → { accepted: true }
```

**为什么不用底层的 `agents.get(id).followup(...)`**：`sessionController.create` 本身是
**create-or-adopt**（活着就直接返回那个 agent、落盘的走 `resume`、都没有才新建），
而且它带一道**子 agent 归属围栏**，`AgentRegistry` 自己没有。走控制器既少写代码，又是
Web UI 已经在走的那条路。

**实测**：`create` 返回 `session-c1b73094-…` + `agentPreset: "standard"`，
`prompt` 返回 `{ accepted: true }`；随后 `liveSessions` / `liveAgents` 都变成 1，
`agents.get(sessionId)` 拿到真实的 Agent 对象。

**`requestId` 是必需的**：它是「持久化在那条被接受的消息上的客户端 id」，inbox 拿 `id`
做唯一性键，重复会抛。文档示例里漏了它。要自己造就用 `crypto.randomUUID()`；更稳的是用
平台自己的 `createUserMessage` —— 实测**可以**从插件里够到（`file:///` 路径下裸
`@deepseek-ai/*` import 解析不了，要走 `createRequire` + 路径列表，`dsh-desktop-mcp`
里已有这个写法），它自己会生成 `id`。

### 5.3 观察回合结束 —— 可以，但 `turn/end` **不等于**「成功」

```js
ctx.on('session/event', (session, event) => { ... })
```

实测一次真实回合收到的（共 33 条 `session/event`）：

```
turn/start(seq 4) → step/start → system/message → user/message → request/header
→ session/title(13) → assistant/attempt → step/end(31) → turn/end(32)
```

事件名是 `event.type`，**不是** `event.kind`（whale-girl 的注释里记着这个坑：
历史上把 kind 当 type 用，导致 turn 边沿永不匹配）。信封是 `{ type, seq, time, data }`。

**关键**：这次 `turn/end` 的 `reason.kind` 是 **`error`**，`reason.error.code` 是 **`SERVER`**
（这台环境连不上模型，重试 7 次后失败）。

所以 `turn/end` **只说明回合结束了，不说明它成功了**。whale-girl 把「非 blocked 的
`turn/end`」一律当成 `done`——照抄的话，**失败的回合会让宠物庆祝**。第 2 期必须按
`reason.kind` 分支：

| `reason.kind` | 宠物该有的反应 |
|---|---|
| `completed` | 完成（庆祝） |
| `error` | 出错（`reason.error.code` 给错误码） |
| `blocked` | 等待批准（waiting） |
| `aborted` / `interrupted` | 被打断 |
| `max-tokens` | 被截断 |

**另外三个可用信号**（都实测到了）：

| 事件 | 载荷 | 用途 |
|---|---|---|
| `agent/status` | `{ agent, status: 'idle' \| 'running' }` | 不用轮询的「忙/闲」 |
| `agent/assistant-stream` | `{ agent, frame }`，`frame.type` 是 `start`/`chunk`/`end` | **逐字流式**，气泡里能边想边显示 |
| `agent/turn-stopping` | `{ agent, turn, signal }`（serial，回合边界提交前 await） | 想在收尾时插一句 |

从普通插件上下文注册的监听是**未打标签**的，会收到**所有**会话的事件，不用挨个订阅。

**没验的**：这台环境连不上模型，所以只观察到 `error` 结尾的回合，**没观察到一次
`completed` 的回合**。上表里除 `error` 外的分支是按 `TurnEndReason` 类型写的，不是实测的。

## 6. 架构

```
主窗口（关掉时隐藏，不退出）
  ├── content webview（DSH 页面）—— 关掉后不工作，所以宠物不依赖它
  └── pet 窗口（常驻，可关）
        ├── 渲染：React + 帧动画（CDN 无依赖，和 tray-menu 同构）
        ├── 壳能力：Tauri IPC（拖拽位置、显隐、开机自启）
        └── 数据：新增一个宿主半插件 plugins/dsh-desktop-pet/
              ├── ctx.webServer 挂同源路由（读会话/发消息/文件队列）
              └── 落盘：<dshHome>/pet/（位置、队列、设置）
```

**关键决定：宠物不依赖主窗口的 webview。** 主窗口关闭时 `content` 可能被销毁，所以宠物要活，它需要的能力必须来自**宿主半插件**（那条路在宿主进程里，和窗口无关）。

## 11. 第 1 期：实际做了什么，以及踩到的两个真 bug

**实现**：`src-tauri/src/pet.rs`（窗口、位置、落盘）、`src/pet.tsx`（宠物本体与交互）、
`src/styles.css` 的 `.pet-*` 段、托盘菜单加一项开关。

**两个在真机上才暴露、光看代码看不出来的问题**：

1. **宠物窗口没有 capability，拖拽和主题监听全被拒绝。**
   `capabilities/default.json` 的 `windows` 列表里没有 `pet`。Tauri v2 的权限是**按窗口**发的，所以
   `startDragging()`（第 1 期的核心交互）和 `listen('theme-changed')` 都会抛权限错误。
   窗口能显示、能摆位置，唯独拖不动——很容易被当成"拖拽实现写错了"。

2. **托盘菜单会把整个应用锁死。**
   `show_tray_menu` 原来在**没有菜单窗口时就地 `build()`**。建 webview 会派发到主线程并等待，
   而它的两个调用方（托盘图标事件、宠物右键命令）本来就跑在主线程上——于是主线程等自己，
   所有 IPC 挂起。这不是宠物引入的：**右键托盘图标本来就会锁死**。
   修法是把菜单窗口在启动时预建好（和更新弹窗、宠物一样），`show_tray_menu` 只负责摆位置和显示。

**顺带修掉的三处坐标问题**：

- 宠物位置改用 `PhysicalPosition` + `SystemParametersInfo(SPI_GETWORKAREA)`。原来混用逻辑像素，
  在缩放环境下会差一个系数。
- 菜单按"可见卡片"而不是"窗口矩形"做边界收拢——窗口带一圈看不见的调整边框（这里左右各 8px、
  上方 1px），按窗口矩形收拢会让卡片正好压出屏幕边缘。
- 托盘图标传来的坐标物理/逻辑混用，缩放下会摆错位置。

**实测过的**（都在运行中的应用里量过，不是看代码推的）：

| 项 | 结果 |
|---|---|
| 默认位置 | `2184,840` = 工作区右下角内缩 24px，精确吻合 |
| 位置记忆 | 拖动后落盘 `x/y/monitor`，重启回到原位 |
| 透明 | 截屏见壁纸透出；页面自身 `html/body/root` 背景均为 `rgba(0,0,0,0)` |
| 待机动画 | `pet-breathe` / `pet-blink` / 耳朵抖动三条都在跑 |
| 被摸反应 | `data-mood` 切到 `happy`，弹跳 + 腮红 + 星星 + 影子收缩，1.1s 后回待机 |
| 减弱动效 | 循环动画停、**点击反应保留**（这是刻意的取舍） |
| 拖动 | `startDragging()` 返回成功 |
| 关主窗口 | 主窗口隐藏、**应用与宠物都还在** |
| 托盘开关 | 显示/隐藏宠物都生效，状态落盘 |
| 右键菜单 | 宠物贴底时**向上展开**，可见卡片完全落在工作区内 |

**没验的**：多显示器、非 100% 缩放、以及"在宠物外面点一下菜单会不会自己收起来"
（这台机器的会话没有交互桌面，合成点击送不到窗口）。

## 12. 第 2 期：状态反映 + 气泡

**实现**：

| 文件 | 干什么 |
|---|---|
| `plugins/dsh-desktop-pet/index.js` | 宿主半：订阅 `session/event`，推出 `GET /dsh-desktop-pet/state` |
| `src-tauri/src/host.rs` | `http_get_body()`：给宿主路由用的最小 HTTP GET |
| `src-tauri/src/lib.rs` | `start_pet_state_watch()`：每 600ms 拉一次，变了就 `emit("pet-state")` |
| `src/pet.tsx` + `src/styles.css` | 六种表情：思考 / 执行工具 / 等待批准 / 完成 / 出错（+ 被摸） |
| `src/pet-bubble.tsx` + `pet-bubble.html` | 气泡窗口：会话标题 + 当前状态 + 最近回合结果 |

**为什么状态走宿主半**：宠物住在桌面上，主窗口关掉时 DSH 页面就没了——而那正是宠物
唯一存在的时刻。所以状态必须在**宿主进程**里推导，那是会话真正所在的地方。

**为什么宠物自己去不了那个路由**：宠物是壳窗口，宿主是另一个源。壳本来就知道宿主在哪，
所以由壳去取、再用 Tauri 自己的事件通道转给宠物。

**表情设计的一条原则**：只用已经存在的零件（眼睛、耳朵、嘴、腮红），不新增图形——
每个表情都是同一只宠物在变，而不是换了一张脸。只有"出错"动颜色（去饱和 + 变暗），
其余全靠姿态：宠物在屏幕角落，余光扫过去时姿态比颜色好读。

### 12.1 一个会毁掉整个应用的真 bug：登录 cookie 无限堆积

**症状**：DSH 页面打不开，显示 `HTTP ERROR 431`。

**根因**：宿主每次启动都会给 Web UI 发一个以 token 命名的登录 cookie
（`dsh-auth-<token>`，30 天有效期），**没有任何东西清理它们**。每次启动多加约 173 字节，
而 Chromium 拒绝发送请求头超过约 2KB 的请求，它自己的基础头部就占掉大半。
实测这台机器上积了 **69 个 cookie、约 15.6KB**，于是应用自己的页面在跑任何一行代码之前
就被 431 拒了。

**这不是宠物引入的**，是启动次数攒出来的——任何人都迟早会撞上。

**修法**：挂载 DSH 之前先清掉上次留下的 cookie，只留本次的。实测这个 webview 里的
cookie **69 个全是登录 cookie**，没有别的东西要保。清理必须**同步做完**再挂载，
因为会撞 431 的正是子 webview 的第一个请求；而且必须**在独立线程上**做——Tauri 明确
记录了这些 cookie 调用在同步命令/事件处理里会死锁。

### 12.2 又一个按窗口发权限的坑：气泡窗口

`pet-bubble` 不在 `capabilities/default.json` 的窗口列表里。后果和宠物当初一样隐蔽：
**窗口能显示、能渲染、样式全对，但收不到 `pet-state` 事件**（所以卡片永远是空的），
Escape 的 `hide()` 也会被拒。症状看起来像"气泡没接上数据"，实际是权限。

> 这已经是同一类问题第二次咬人了（第 1 期是宠物拖不动）。**新增任何窗口，先看
> `capabilities/default.json` 的 `windows` 列表里有没有它。**

### 12.3 实测过的

一次真实回合的完整链路（宿主发布 → 壳轮询 → Tauri 事件 → 宠物换脸）：

```
20:09:23  host=idle     | pet mood=idle
20:09:23  host=thinking | pet mood=thinking   ← turn/start
20:09:38  host=error    | pet mood=thinking
20:09:39  host=error    | pet mood=error      ← 约一拍（600ms）后跟上
20:09:53  host=idle     | pet mood=error
20:09:54  host=idle     | pet mood=idle       ← 15s 错误停留期结束
```

**关键**：它显示的是 `error` 而**不是** `done`。whale-girl 把"非 blocked 的 `turn/end`"
一律当完成——照抄的话**失败的回合会让宠物庆祝**。这条差异是实测出来的，不是推的。

气泡在回合中打开的内容（与宿主一致）：

```json
{ "tone": "busy", "state": "正在思考…", "session": "probe12 ok", "foot": "第 1 回合 · 点宠物关闭" }
```

六种表情逐项量过计算样式，每个都确实不同（耳朵角度、眼睛缩放、嘴形、忙碌点）。

### 12.4 顺带发现的第三个问题（**还没修**）

调试时 UI 发消息一直被服务端拒绝：

```
SessionAlreadyOwnedError: session "..." is already owned by an active write handle
```

根因不在产品逻辑，在**强杀**：我反复用 `Stop-Process -Force` 杀壳进程，那样**不会走
`RunEvent::Exit`**，于是它 spawn 的 DSH 宿主被留成孤儿。实测积了 **12 个孤儿宿主**
（最早一个是 9/21 的），每个都占着会话的写租约。

**这对用户也是真的**：应用崩溃、或者从任务管理器结束进程，都会留下孤儿宿主，
而症状是"发消息没反应"——非常难查。修法是启动时清理父进程已死的 DSH 宿主，
需要枚举进程（`CreateToolhelp32Snapshot`），这次没做。
