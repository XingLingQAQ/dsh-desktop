Stop the host surviving a force-kill, and let the pet send messages

Two things, in that order: first the bug that made sessions un-sendable, then
phase three.

The orphaned host is fixed with a kill-on-close job object rather than by
cleaning up on the next launch. The previous plan was wrong in principle: it
relied on cleanup code running, and the whole problem is that cleanup code does
not get to run. JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE makes it the kernel's job --
the OS closes a process's handles when it dies, however it dies, so the host goes
with the shell even when the exit handler never executes. The handle is
deliberately leaked, because closing it is the trigger. Verified: force-kill the
shell and the host is gone, with zero children left.

Worth recording why "kill every DSH host at startup" would have been wrong: this
machine runs other DSH hosts, including the one executing the agent, and a name
match would have killed it too. A job object only ever covers the child we made.

Phase three adds sending and session switching. The host gains
GET /sessions (live union persisted, capped, with a live flag), POST /prompt, and
POST /select; the shell exposes them as three Tauri commands; the bubble gains a
session picker and a composer.

Picking a session pins the pet to it, and a new turn in a different session drops
the pin -- following the most recently active session is right by default and
wrong the moment someone deliberately points the pet at one, but a pin that
outlives the user visibly moving on is worse than no pin.

Refusals pass through verbatim, because the reason is the useful part. A real one
is SessionAlreadyOwnedError: session "..." is already owned by an active write
handle, and it is exactly what led to the orphaned-host bug above; replacing it
with "send failed" would have hidden it. The bubble's window grew by 16px so that
message fits without hovering.

Verified end to end: select a session in the bubble, send from the pet, the turn
runs, the title is learned, and the face and state follow. Failure paths checked
too -- empty text and a missing session id both come back as invalid-request with
a readable message.
